## Authentication model

### Access-token authentication

Protected endpoints require:

```http
Authorization: Bearer <signed-access-token>
```

The access token identifies the user through `sub` and the persisted session through `sid`. The server validates the signature, key ID, algorithm, issuer, audience, token type, time claims, session ownership, session status, and account state before executing a protected route.

Access tokens do not contain roles or permissions. Current authorization is loaded from PostgreSQL.

### Refresh-token authentication

`POST /api/v1/auth/token/refresh` and `POST /api/v1/auth/logout` do not require an access token. They require a signed refresh token in the JSON body. Refresh tokens are rotated and must be treated as secrets.

### Administrative authorization

Administrative endpoints require both:

1. A valid bearer access token bound to an active session.
2. The endpoint-specific permission resolved from PostgreSQL.

The access token itself is not the source of the permission decision.

## Request headers

### Shared tracing headers

| Header | Required | Behavior |
| --- | --- | --- |
| `X-Request-ID` | No | Must be a valid UUID when supplied. Generated by the service when omitted. Returned in response metadata and headers. |
| `X-Correlation-ID` | No | Must be a valid UUID when supplied. Used to correlate related calls. Generated or inherited according to middleware policy. |
| `User-Agent` | No | Captured as observational session metadata during approved session workflows. It is not an authentication factor. |

### Public authentication metadata

| Header | Required | Behavior |
| --- | --- | --- |
| `X-Client-ID` | No | Rate-limit and client-context dimension. It does not identify a user. |
| `X-Device-ID` | No | Rate-limit dimension or session device metadata. A stored device binding cannot be replaced during refresh. |
| `X-Platform` | No | Session metadata. Accepted values are `web`, `android`, `ios`, or `service` where declared. |
| `X-Device-Type` | No | Session metadata such as `desktop`, `mobile`, or an approved client value. |

`X-User-ID` and `X-Session-ID` are not supported. Identity comes from signed JWT claims and the persisted session.

## Error handling

| HTTP status | General meaning |
| --- | --- |
| `400 Bad Request` | Malformed request or invalid request/correlation header. |
| `401 Unauthorized` | Missing, invalid, expired, replayed, or wrong-type token; invalid OTP; invalid password; inactive session; invalid reset proof. |
| `403 Forbidden` | Authenticated principal lacks the required role or permission. |
| `404 Not Found` | Resource or route not found. Some security flows intentionally avoid exposing resource existence. |
| `409 Conflict` | Duplicate identity/code, invalid state transition, optimistic-lock conflict, or database integrity conflict. |
| `413 Payload Too Large` | Request exceeds `MAX_REQUEST_BODY_BYTES`. |
| `422 Unprocessable Entity` | Pydantic validation or application policy validation failed. |
| `429 Too Many Requests` | Rate limit, OTP cooldown, resend limit, or verification-attempt limit exceeded. |
| `500 Internal Server Error` | Unexpected server error; implementation details are hidden. |
| `503 Service Unavailable` | PostgreSQL, Redis, or another required dependency is unavailable. |
| `504 Gateway Timeout` | A bounded infrastructure operation exceeded its configured deadline. |

Authentication errors include `WWW-Authenticate: Bearer`. Rate-limit responses may include `Retry-After`. Error responses use `Cache-Control: no-store`.

## Client integration guidance

### Token storage

- Treat access tokens, refresh tokens, reset proofs, OTP values, and passwords as secrets.
- Do not write them to application logs, analytics events, URLs, or error monitoring breadcrumbs.
- Discard the previous refresh token immediately after a successful refresh.
- When logout-all succeeds, clear all local authentication state because the current session is revoked too.

### Authorization data

- Call `GET /api/v1/auth/users/me/authorization` after authentication when the client needs role- or permission-based UI state.
- Refresh authorization after an administrator changes role assignments or permissions.
- Never rely on hidden buttons as a security control. Backend endpoints enforce permissions independently.

### OTP flows

- Preserve the returned `challenge_id` and submit it with the same destination and purpose during verification.
- Respect `retry_after_seconds` and HTTP `Retry-After` values.
- Do not expose OTP codes in production. `development_otp` should remain `null` outside explicitly controlled local environments.

### Request IDs

- Generate UUID request and correlation IDs when the client requires end-to-end tracing.
- Store the returned IDs alongside client-side error reports, not alongside credentials.

### API evolution

- Generate clients from `/openapi.json` only when documentation is enabled in the target environment.
- Treat strict request models as intentional. Unknown request properties return HTTP 422.
- Administrative permission codes are stable security contracts and should be changed only through coordinated migrations.

### Production readiness

- Connect an approved email/SMS provider before enabling OTP-dependent production workflows.
- Use RS256 and publish JWKS when external services validate tokens.
- Use Redis-backed rate limiting for staging and production.
- Run PostgreSQL integration tests for refresh locking, OTP concurrency, session revocation, and authorization joins.

For architecture and deployment details, see [`Architecture.md`](Architecture.md), [`deployment_guide.md`](deployment_guide.md), and [`script_commands.md`](script_commands.md).
